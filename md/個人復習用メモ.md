## 課題番号：19（Integerの==比較 -- オートボクシング問題編）
 
**① 該当箇所**
- OrderService.java(120行目)：paymentMethodJudge()
**② なぜ問題なのか**
`order.getPaymentMethod()`はInteger型を返すため、`== 1`での比較はオートボクシング問題の対象になる。JavaのIntegerキャッシュは-128〜127の範囲のみ同じインスタンスを使い回すため、その範囲外の値が返ってきた場合に`==`比較が必ずfalseになる。
 
**③ なぜこのように修正したのか**
`getPaymentMethod()`がInteger型で返ってくる設計を維持しつつ、`.equals()`で比較する形に修正した。また左辺を定数側（`Integer.valueOf(1)`）にすることで、`getPaymentMethod()`がnullを返してもNPEが発生しない安全な比較ができる。int型にunboxingする方法もあるが、nullを返す可能性がある場合はunboxing時にNPEが発生するリスクがあるため、Integer型のまま`.equals()`で比較する方が安全。
 
**④ 気づきや他の改善策**
- `Objects.equals(order.getPaymentMethod(), 1)`を使う方法もあり、こちらも左辺がnullでもNPEが発生しない。
- 根本的にはenumに変換する設計が望ましい（課題#1参照）。
**⑤ 編集例**
 
修正前：
```java
if (order.getPaymentMethod() == 1) {
```
 
修正後：
```java
// #19 '=='の比較によるオートボクシング防止
if (Integer.valueOf(1).equals(order.getPaymentMethod())) {
```
 
**⑥ 学んだ概念・用語**
- オートボクシング・アンボクシング
- IntegerキャッシュとNPEのリスク（-128〜127の範囲外）

## 課題番号：35（innerHTMLのXSSリスク編）

**① 該当箇所**
- item_detail.html：appendMessage()

**② なぜ問題なのか**
`innerHTML`にユーザー入力を埋め込む場合、入力値がHTMLとして解釈されるため悪意のあるスクリプトが実行されるXSSのリスクがある。既存の`escapeHtml()`で`&`・`<`・`>`はエスケープされていたが、クォート（`"`・`'`）のエスケープが漏れており、また将来的にエスケープ処理が漏れるリスクも残っていた。

**③ なぜこのように修正したのか**
`innerHTML`の代わりに`textContent`を使うことで、入力値をHTMLとして解釈せず純粋なテキスト文字列として扱うようにした。これによりスクリプトを含む入力値もそのまま文字として表示されるだけになり、XSSリスクを根本的に排除できる。改行の表現は`white-space: pre-wrap`をCSSで指定することで対応し、不要になった`escapeHtml()`はコメントアウトした。

**④ 気づきや他の改善策**
- `resetChat()`内の`innerHTML`は固定文字列のためXSSリスクなし。今回は対象外。
- `escapeHtml()`は不要になったため最終的には削除できる。
- Thymeleaf側では`th:text`が自動でXSSエスケープを行うため、サーバーサイドは安全。`th:utext`は行わないので注意。

**⑤ 編集例**

修正前：
```javascript
function appendMessage(role, text) {
    const div = document.createElement('div');
    div.className = role === 'user' ? 'chat-msg-user' : 'chat-msg-ai';
    div.innerHTML = '<span>' + escapeHtml(text) + '</span>';
    messages.appendChild(div);
    messages.scrollTop = messages.scrollHeight;
}
```

修正後：
```javascript
// リファクタリング課題#35 innerHTMLをtextContentに変更しXSSリスクを低減
function appendMessage(role, text) {
    const div = document.createElement('div');
    div.className = role === 'user' ? 'chat-msg-user' : 'chat-msg-ai';
    const span = document.createElement('span');
    span.textContent = text;
    span.style.whiteSpace = 'pre-wrap';
    div.appendChild(span);
    messages.appendChild(div);
    messages.scrollTop = messages.scrollHeight;
}
```

**⑥ 学んだ概念・用語**
- XSS（クロスサイトスクリプティング）
- `innerHTML`と`textContent`の違い
- 正規表現の`g`フラグ（全体置換）
- `white-space: pre-wrap`による改行表現
- `escapeHtml()`のエスケープ漏れ（クォート）

## 課題番号：33（varとlet/constの使い分け編）

## 課題番号：1（安全な状態遷移 -- OrderStatus enum編）※更新

**追加対応の方針**

- リファクタリングでenumの内部値を変更しても、Java側のenumだけ直せばよく、Viewの追随漏れという同種の問題を再発させにくい設計にできた

## 課題番号：4（安全なオブジェクト生成 -- Builderパターン編）※レビュー対応で更新

**① 該当箇所**
- Order.java：Builderパターン追加、setter削減（追加対応）
- OrderControler.java：orderCompletion()（Builderにstatus・userIdを含める形に変更）
- OrderService.java：order()（setStatus・setUserIdの呼び出しを削除）
- OrderRepositoryTest.java：setUp()、insert_正常系_注文情報が保存される()、findByOrdertable_別ユーザーは取得されない()（連鎖修正）
- OrderServiceTest.java：createSampleOrder()、PaymentMethodJudgeテストクラス、OrderMethodテストクラス、AdditionalTestsクラス、sendMail_PaymentMethod2()（連鎖修正）

**② なぜ問題なのか**
初回対応（Builderパターン導入）ではBuilderを実装したものの、既存の全setterと引数なしコンストラクタをそのまま残していた。そのため`new Order()` + setterで`build()`の必須チェックを完全に迂回でき、不完全な`Order`が作れてしまう状態だった（レビュー指摘）。

`Order.Builder.build()`の中にのみ必須項目チェックが書かれており、`new Order()`や各setterにはチェックが一切ない。「正面玄関に鍵をかけても、鍵のかかっていない裏口がある」状態で、setterを使えば必須チェックをすり抜けて`Order`を組み立てられてしまうことが問題の本質だった。

**③ なぜこのように修正したのか**
以下の方針で対応した。

1. `Order`を生成できる経路を`Order.builder()...build()`の1つだけに限定する
2. ただし、全てのsetterを一律に削除すると、`Order`生成後に段階的に値を確定させる必要がある処理（DBの自動採番、SQL結果の複数行読み込みによる組み立て）が壊れてしまうため、以下の3つのsetterのみ残した

   - `setUser()`：`OrderRepository`の`ORDER_RESULTSET`で、`Order`生成後にJOIN結果から組み立てた`User`を紐付けるため必要
   - `setOrderItemList()`：同上、`OrderItem`をループで1件ずつ読み込みながら組み立てるため必要
3. `status`・`userId`は、Builder呼び出し前（`OrderControler`側）で確定できる情報だったため、`OrderService.order()`内の`setStatus()`・`setUserId()`は削除し、呼び出し元でBuilderに含める形に変更した
4. `paymentMethodJudge()`は`Order`ではなく`Integer paymentMethod`を直接受け取る形に変更し、Builder組み立て前でも判定できるようにした

「削除してよいsetter」と「残すべきsetter」の判断基準は、**Builderの`build()`を呼ぶ前に全ての値が揃えられるか（削除可）／生成後に段階的にしか値が確定しないか（残す必要あり）**という観点で切り分けた。

**④ 気づきや他の改善策**
- setterの削減は`Order.java`単体では完結せず、`OrderRepository`・`OrderService`・`OrderControler`・両テストファイルまで連鎖的に影響が及んだ。ドメインオブジェクトの生成方法を変えるリファクタリングは、想定より影響範囲が広くなりやすいと実感した
- テストコードの修正は今回の課題スコープ外だが、コンパイルを通すために必須だったため対応した。テストが実装の変更に強く依存している場合、リファクタリングのコストがテストコード側にも及ぶことを学んだ

## 課題番号：5（スレッド安全——在庫の同時購入編）

**① 該当箇所**
なし（実際のコードに該当箇所が存在しなかった）

**② なぜ問題なのか**
課題文の問題ありコード（CartService.addItemToCart()）では、①カートを取得→②新規作成または既存取得→③商品を登録、という流れの中で在庫チェックが一切行われていない。在庫1個の商品に対してユーザーAとBが同時に①のカート取得処理を実行すると、両者とも「まだ在庫がある状態」を見た状態で③の商品登録まで進んでしまう。Aの登録がBの取得より先にコミットされていたとしても、Bは古い（Aの変更を反映していない）情報をもとに処理を続けてしまうため、在庫が1個しかないのに2人分の注文が通ってしまう。`@Transactional`は「1つのトランザクション内の処理が途中で失敗したら全部ロールバックする」ことは保証するが、「他のトランザクションが同時に何を読んでいるか」までは制御しないため、このレースコンディションを防げない。

**③ なぜこのように修正したのか**
楽観的ロック（versionカラム）を使うことで解決する。UPDATE文のWHERE句に「操作開始時に読んだversionと一致するか」を条件として入れることで、自分が読んだ後に誰かが先に更新していないかを検知できる。先に更新した1人だけがversion一致で成功し、後から来た人はversionが変わっているためWHERE条件に合う行がなく更新0件となり、`OptimisticLockException`が発生する。厳密には「ロールバック」ではなく「そもそもUPDATEが1行も更新されなかった」という結果を受けてアプリ側が例外を投げている、という流れ。

実際のプロジェクトでは`ToppingRepository.decrementStock()`がすでに近い考え方（在庫確認と減算を1本のUPDATE文にまとめる方式）で実装されており、TOCTOU（Time-of-Check to Time-of-Use）問題が構造的に起こらない設計になっていたため、今回は「該当なし」と判断した。

**④ 気づきや他の改善策**
- versionカラムはBIGINT型（約922京まで扱える）で定義するため、桁数の枯渇や検索速度への影響は実務上問題にならない。固定長のデータ型なので値の大小でパフォーマンスが変わることもない
- 楽観的ロックは「競合が稀なケース」に向いている設計。1000人規模が同時に同じ1商品へ殺到するようなケースでは、リトライが雪崩のように増える（リトライストーム）ため不向き。その場合は悲観的ロック（SELECT FOR UPDATE、行ロックで順番待ちさせる）や、DB前段でのキャッシュ管理（Redis等）が適している
- 本ECサイトはカレーのカスタム注文という性質上、通常利用では極端な同時アクセスは想定しにくいため、楽観的ロックで十分機能すると判断できる
- `ToppingRepository.decrementStock()`は`UPDATE ... WHERE stock_amount >= :amount`という形で「在庫確認」と「減算」を1本のSQLにまとめており、これは楽観的ロックのversion方式とは別のアプローチだが、同じく「TOCTOU問題を1本のアトミックなSQLで解消する」という考え方は共通している

## 課題番号：6（拡張性のある設計——支払い方法編）

**① 該当箇所**
- OrderService.java：paymentMethodJudge()
- PaymentMethod.java：新規作成
- PaymentProcessor.java：新規作成
- CashOnDeliveryPaymentProcessor.java：新規作成
- CreditCardPaymentProcessor.java：新規作成

**② なぜ問題なのか**
`paymentMethodJudge()`は`if-else`で支払い方法を2択（1かそれ以外か）でしか判定できない構造になっていた。3つ目の支払い方法（例：後払い）を追加すると、区別できずにすべて代引き扱いになってしまう。また、新しい支払い方法を追加するには`paymentMethodJudge()`自体を直接書き換える必要があり、既存のクレジットカード・代引きの判定ロジックを誤って書き換えてしまうリスクがあった。1と2という数字が何を意味するかもコードから読み取りにくく、マジックナンバー化していた。

**③ なぜこのように修正したのか**
Strategyパターンを導入し、支払い方法ごとに専用のクラス（`CashOnDeliveryPaymentProcessor`、`CreditCardPaymentProcessor`）を作り、共通のインターフェース（`PaymentProcessor`）を実装させた。`OrderService`は`List<PaymentProcessor>`をコンストラクタで受け取り、`Map<PaymentMethod, PaymentProcessor>`に変換して保持する。`paymentMethodJudge()`は「Integer→PaymentMethod変換→Mapから該当するProcessorを取得→judge()を呼ぶ」という共通の手順だけを行い、支払い方法ごとの具体的な判定ロジックは一切持たない設計にした。

これにより、新しい支払い方法を追加する際は`@Component`をつけた新しいクラスを1つ追加するだけで済み、`OrderService`（既存コード）を一切変更する必要がなくなった。新しいクラスを追加する作業と、既存のクラスを書き換えてしまうリスクが完全に分離されたため、既存の判定ロジックを誤って壊してしまう可能性がなくなった。

支払い方法の種類（`PaymentMethod`）と、種類ごとの振る舞い（`PaymentProcessor`）を分けて設計した理由は、`OrderStatus`（課題1）とは異なり、支払い方法は将来的に「種類ごとに異なる処理」が発生しうる性質を持つと考えたため。enumだけでは値の区別はできても、種類ごとに異なる処理を安全に追加していく仕組みは作れない。

また、HTML（`order_confirm.html`）側の`value`が「1=代引き、2=クレジットカード」となっていたのに対し、`OrderService`の旧ロジックは逆の対応（1=支払い済み扱い）になっているという矛盾を発見した。既存のHTML側の値を正として`PaymentMethod`を`CASH_ON_DELIVERY(1)`、`CREDIT_CARD(2)`と定義し、Java側をHTMLに合わせて修正した。

**④ 気づきや他の改善策**
- 支払い方法を追加しても現状は`judge()`（ステータスを1つ返すだけ）しか処理がなく、「将来処理が増える」という前提が今のコードのどこにも書かれていない点は、YAGNI原則（使わない機能は作るな）との緊張関係がある。ただし今回は課題文が明示的にStrategyパターンの実践を求める学習目的の課題であるため、あえてこの設計を選択した
- `List`から`Map`への変換は、課題40（O(n²)問題）・課題28（型安全コレクション）で使った`Collectors.toMap()`と同じパターンで実装できた
- `OrderService`のコンストラクタインジェクション化は、課題18で`CartService`に対応した内容の横展開になった。合わせて対応したことで、課題18の未対応リストが1つ減った

- 実装中、HTMLとJavaの対応関係の矛盾（1と2の意味が逆転していた）に気づいたのは、課題6の作業がきっかけだった。既存のマジックナンバーを整理する作業は、こうした隠れた不整合を発見するきっかけになると実感した

## 課題番号：26（Template Methodパターン——注文処理フロー編）

**① 該当箇所**
なし（実際のコードに該当箇所が存在しなかった）

**② なぜ問題なのか**
課題文の問題ありコードでは、`CreditCardOrderService`と`CodOrderService`という2つのクラスに、それぞれ`processCreditCardOrder()`・`processCodOrder()`というメソッドがあり、バリデーション・在庫チェック・ステータス更新・メール送信という共通処理が、決済処理（クレジットカード決済／代引き登録）を挟んで両方のクラスに重複して書かれていた。

共通処理が複数のクラスに点在していると、修正のたびに全箇所を漏れなく直す必要があり、書き換えミスが起こりやすい。例えば、共通処理の実行順序を変更したい場合、片方のクラスだけ修正して、もう片方を直し忘れると、支払い方法によって処理の順序がズレてしまう（例：クレジットカード決済だけ「決済→在庫チェック」の順になり、在庫切れの商品が先に決済されてしまう、といった業務上の不具合につながりかねない）。保守性・拡張性の観点からも、共通部分を1箇所にまとめておくべきだった。

**③ なぜこのように修正したのか**
Template Methodパターンでは、共通の処理の流れを抽象クラス（`OrderProcessor`）の`process()`メソッドにまとめ、支払い方法ごとに異なる部分（決済処理）だけを`processPayment()`という抽象メソッドとして切り出し、サブクラス（`CreditCardOrderProcessor`・`CodOrderProcessor`）に実装させる設計にする。

`process()`メソッドには`final`をつける。これにより、サブクラス側が`process()`自体を上書きして、共通処理の実行順序を勝手に変更することができなくなる。`final`がなければ、Template Methodパターンで統一したはずの流れが、サブクラスごとに再び崩れてしまうリスクが残るため、`final`は「流れを統一する」という設計意図を強制的に守らせるために必須の要素である。

なお、このプロジェクトの実際の注文処理（`OrderService.order()`）は、支払い方法ごとに分かれた別々のクラスが存在せず、1つのメソッドに統一されているため、課題文が指摘する「重複」自体がそもそも発生していなかった。課題6（Strategyパターン）で支払い方法ごとの`status`判定のみを`PaymentProcessor`に分離したが、それ以外の注文処理フロー（在庫確認・カート処理・DB保存）は元々1本の共通処理として書かれていたため、該当なしと判断した。

**④ 気づきや他の改善策**
- Template Methodパターン（継承ベース）とStrategyパターン（コンポジションベース、課題6で対応）は、どちらも「変わる部分」と「変わらない部分」を分離するという目的は共通しているが、実現方法が異なる。Template Methodは「流れ（順序）」を固定したい場合に向いており、Strategyは「部品（振る舞い）」を丸ごと入れ替えたい場合に向いている
- もし将来、`OrderService.order()`が支払い方法によって処理の順序自体を変える必要が出てきた場合（例えば代引きのみ在庫確保の仕組みを変える等）、Template Methodパターンの導入を検討する余地がある。ただし現状はそのような分岐要件がないため、無理に導入する必要はないと判断した
- `final`修飾子は、メソッドだけでなくクラスにもつけられる（継承自体を禁止する）。今回はメソッド単位の話だったが、クラス全体を継承させたくない場合にも同じ考え方が使える

## 課題番号：7（変更の波及を防ぐ——注文完了時の処理編）

**① 該当箇所**
- OrderControler.java：orderCompletion()（order()とsendMail()の呼び出し部分）
- OrderService.java：order()（イベント発行の追加）
- OrderCompletedEvent.java：新規作成
- OrderMailListener.java：新規作成

**② なぜ問題なのか**
`OrderControler`が`order()`（注文確定）と`sendMail()`（メール送信）を両方呼び出しており、「順番に呼び忘れず実行する責任」が呼び出し元に押し付けられていた。`order()`と`sendMail()`は別々の独立したメソッド呼び出しのため、どちらか一方の呼び出しをうっかり削除・忘れてしまっても、コンパイルエラーにはならず実行時まで気づけない。実際に呼び忘れが起きると、注文自体は成立するのにメールが送られない、という不具合につながる。

また、注文完了時に新しい処理（スタンプ付与、在庫アラートなど）を追加するたびに、`OrderControler`や`OrderService.order()`に処理を継ぎ足していくことになり、`OrderControler`が本来の役割（画面遷移の制御）を超えて肥大化していくリスクがあった。

**③ なぜこのように修正したのか**
Observerパターン（Spring `ApplicationEvent`）を導入し、`OrderService.order()`は「注文完了イベント」を発行するだけにし、メール送信などの実処理はリスナー側（`OrderMailListener`）に任せる設計にした。呼び出し元（`OrderControler`）は`order()`を呼ぶだけで済むようになり、メール送信という処理の存在自体を`OrderControler`が知る必要がなくなった。

実装にあたり、以下の設計判断を行った。

- `sendMail()`メソッド自体（中身のロジック）は`OrderService`に残し、**呼び出しのタイミングだけ**をイベント駆動にした。理由は、`sendMail()`のロジックごと`OrderMailListener`に移してしまうと、既存のテストコード（`OrderServiceTest`の`SendMail`テストクラス）が対象を見失って壊れてしまうため。影響範囲を最小限に抑える設計とした
- `OrderCompletedEvent`には`email`と`orderId`の2つの情報を持たせた。`email`は`Order`オブジェクトの`user`フィールドがBuilder経由では設定されないため（`OrderRepository`側でのみ設定される）、`order()`の引数に`String email`を追加し、`OrderControler`から明示的に渡す形にした
- 実装当初、「処理が1つ（メール送信）しかない現状で、Observerパターンをフル導入するのはオーバーエンジニアリングではないか」という議論があった。今の問題（呼び出し順序を呼び出し元に依存している）自体は`order()`内で`sendMail()`を直接呼ぶだけでも解決できるが、今回は課題文の意図（Observerパターンの実践）を優先し、フル実装する方針とした
- `OrderControler`側の`sendMail()`直接呼び出し（try-catchブロック）は、二重送信を防ぐため削除（コメントアウト）した

**④ 気づきや他の改善策**
- Observerパターンはリスナー間の処理順序を保証しない点に注意が必要。メール送信の前に必ず在庫確定処理を終えたい、といった順序依存がある場合は、Observerパターンではなく別の設計（同期的な呼び出し）を検討する必要がある
- `@Async`をつけると非同期でリスナーを実行できる。メール送信のような時間がかかる処理は、非同期化することでレスポンス速度の改善も見込める（今回は未実装）
- Template Method（課題26、継承ベース）・Strategy（課題6、コンポジションベース）・Observer（課題7、イベント駆動）は、いずれも「変わる部分と変わらない部分を分離する」という共通の目的を持ちながら、実現方法が異なる。Observerは「1つの出来事に対して、複数の無関係な処理が反応する」場面に向いている
- 「今は処理が1つしかないのに、フレームワーク級の仕組みを持ち込む」というYAGNI原則との緊張関係は、課題1・課題6でも出てきた論点と同じ構造だった。今回は「課題文の意図を尊重する」という判断で実装したが、実務であれば「本当に複数の処理が今後追加される見込みがあるか」を確認してから導入すべき設計判断である
- `OrderCompletedEvent`が`ApplicationEvent`を継承する設計にしたが、Spring 4.2以降は任意のオブジェクトをイベントとして発行できる（`ApplicationEvent`の継承は必須ではない）。今回は明示的にイベントであることを示すため継承する形を選んだ

上長レビューで「メール送信が失敗したら注文自体もロールバックされるのでは？

で実行されるため、`OrderMailListener.onOrderCompleted()`内で例外が発生すると
`publishEvent()`の呼び出し元である`order()`まで伝播し、`@Transactional`の
デフォルトのロールバック対象（RuntimeException）に該当してしまうことが分かった。

対応案として以下の2つを検討した。
- 案A：`@TransactionalEventListener(phase = AFTER_COMMIT)`にし、注文確定後に
  メール送信を試みる（メール失敗が注文に影響しなくなるが、失敗をお客様にその場では
  伝えられない）
- 案B：`OrderMailListener`内でtry-catchし、例外を握りつぶしてログにのみ記録する
  （疎結合の観点からはやや後退するが、シンプルで確実）

案Bの方向で問題ない、という回答をもらった。理由として、Observerパターンの目的は
「OrderServiceがイベントを発行するだけで完結し、受け取った側（Listener）が
何をするか・失敗時にどう振る舞うかはListener側の責務になる」という考え方であり、
catchする場所さえListener内であれば、OrderService側の疎結合性は崩れない、
という指摘だった。

自分は当初「catchする場所はOrderService.order()の中」だと思い込んでいたため、
「疎結合から外れる」と誤解していた。実際にはcatchする場所を1段階変えるだけで、
疎結合を保ったまま安全性も確保できることに気づけた。

## 課題番号：17（オブジェクト生成の責務——Factory Method編）

**① 該当箇所**
- CartController.java：inCart()
- CartItem.java：from()（新規追加）
- OrderService.java：insertOrderItem()
- OrderItem.java：from()（新規追加）

**② なぜ問題なのか**
`CartController.inCart()`では、`new CartItem()` + `BeanUtils.copyProperties(form, cartItem)` + 複数のsetter呼び出しでオブジェクトを組み立てていた。`BeanUtils.copyProperties()`はフィールド名が一致していれば、意味が違っていても機械的にコピーしてしまう。実際に`form.id`（商品ID）が`cartItem.id`（カート商品の主キー）へ誤ってコピーされてしまうため、`cartItem.setId(null)`という後付けの処理でそれを打ち消していた。

これは「オブジェクトが正しい状態でしか作れない」という保証がどこにも存在せず、`setId(null)`のような帳尻合わせで運用回避している状態だった。また、この組み立て手順が1箇所にまとまっていないため、同じような処理を別の画面・機能で書く場合、開発者が意図しないコピー（誤って主キーに別の値が入るなどの地雷）を自力で踏んでしまうリスクがあった。

`OrderService.insertOrderItem()`でも同様に`BeanUtils.copyProperties(cartItem, orderItem)`が使われており、`CartItem.id`（カート商品の主キー）が`OrderItem.id`（注文商品の主キー）へ誤ってコピーされる、全く同じ構造の問題を抱えていた。こちらは`setId(null)`のような打ち消し処理すらなく、`OrderItemRepository.order()`のINSERT文に`id`カラムが含まれていなかったために、たまたま実害が表面化していなかっただけだった。

**③ なぜこのように修正したのか**
静的ファクトリーメソッド`from()`を、`CartItem`・`OrderItem`それぞれに追加した。必要なフィールドだけを引数として明示的に指定して組み立てるため、余計な値（`id`）がそもそも入り込む余地がない。これにより、バグが起きた後に「防ぐ」設計（`setId(null)`のような後付けの帳尻合わせ）から、そもそもバグが「起こりえない」設計に変わった。

`CartItem.from(ItemCartInForm form, Integer price)`は、`name`・`size`・`itemId`（`form.getId()`から。ここが誤りやすい箇所）・`itemPrice`・`quantity`・`imagePath`をセットし、`id`には一切触れない（Javaの仕様上、`Integer`型フィールドは何も代入しなければ自動的に`null`のままになる）。

`OrderItem.from(CartItem cartItem, Integer orderId)`も同様に、`itemId`（`cartItem.getItemId()`から。`cartItem.getId()`との取り違えに注意が必要だった）・`quantity`・`size`をコピーし、`orderId`は引数として外部から受け取る。`id`には触れない。

呼び出し側（`CartController`・`OrderService`）は、それぞれ`CartItem.from(form, service.getPriceSize(form))`・`OrderItem.from(cartItem, orderId)`という1行に置き換わり、`BeanUtils`への依存もなくなったため、使われなくなった`import org.springframework.beans.BeanUtils;`も削除した。

**④ 気づきや他の改善策**
- `from()`の実装中、`itemId`の取得元を`cartItem.getId()`（誤り）と`cartItem.getItemId()`（正しい）で取り違えるミスを実際に犯した。これは今回の課題が警告していた「名前が似ている別フィールドの取り違え」そのものであり、Factory Methodパターンを導入しても、実装者が中身のロジックを誤れば同じ種類のミスが起きうることを実感した。パターンの導入は「仕組みとして防ぐ」ことはできても、「実装時の注意」自体を代替するものではない
- `OrderItem`側は`setId(null)`のような打ち消し処理が元々存在せず、実害が出ていなかったのは`OrderItemRepository.order()`のSQLに`id`カラムが含まれていなかったという偶然に過ぎなかった。「バグが表面化していない」ことと「バグが存在しない」ことは別であるという、これまでの課題（課題4・課題6）でも繰り返し出てきた教訓が、今回も当てはまった
- `BeanUtils.copyProperties()`は便利だが、型チェックがなくリファクタリングに弱い。フィールド名の一致だけでコピー可否が決まるため、クラスの設計変更（フィールド名変更やリネーム）に対して脆い
- Effective Java Item 1（コンストラクタの代わりに静的ファクトリーメソッドを検討せよ）の実践。静的ファクトリーメソッドは名前をつけられるため、`new CartItem()`より`CartItem.from(form, price)`の方が意図が伝わりやすい

## 課題番号：25（Decoratorパターン——メール送信の拡張編）

**① 該当箇所**
なし（実際のコードに該当箇所が存在しなかった）

**② なぜ問題なのか**
課題文の問題ありコードでは、`OrderService.sendMail()`にログ機能・リトライ機能を直接書き足そうとしている。

```java
public void sendMail(Order order, String email) {
    try {
        sender.send(message);
        logger.info("メール送信完了: {}", email);
    } catch (Exception e) {
        Thread.sleep(1000);
        sender.send(message);
    }
}
```

`sendMail()`に直接リトライやログを書き足すと、1つのメソッドが複数の責任（送信・ログ・リトライ）を抱え込み、単一責任の原則に反する。修正のたびに既存のメール送信ロジックに影響を与えるリスクがあり、機能ごとに個別にテストすることも難しくなる。「リトライなし」「リトライあり」「ログあり」など組み合わせを変えたいとき、複数バージョンのメソッドが増えていくおそれもある。

実際のプロジェクトの`OrderService.sendMail()`は、リトライ・ログ・メトリクス収集などを複数バージョン重ねて実装しているような状態は存在せず、シンプルにメール送信ロジックのみを持っていたため、該当なしと判断した。

**③ なぜこのように修正したのか**
Decoratorパターンでは、`MailService`インターフェースを定義し、基本実装（`SimpleMailService`）を、`LoggingMailService`・`RetryableMailService`のようなラッパークラスで包む（デコレートする）。各ラッパークラスは`MailService`型のフィールド（`delegate`）を保持し、実際の送信処理はそのフィールドに**委譲**する。自身は送信の前後に、ログ出力やリトライなど、自分の責任範囲の処理だけを追加する。

`LoggingMailService`が`SimpleMailService`を包み、さらに`RetryableMailService`が`LoggingMailService`を包む、というように「玉ねぎのように」複数のDecoratorを重ねられる。これにより、新しい機能（メトリクス収集など）を追加したいときも、既存のクラス（`SimpleMailService`・`LoggingMailService`・`RetryableMailService`）には一切触れず、新しいクラス（`MetricsMailService`）を1つ追加し、Beanの組み立て方（`@Bean`メソッド内の入れ子）を変えるだけで済む。

**④ 気づきや他の改善策**
- Decoratorパターンは「継承ではなくコンポジションで機能を追加する」という点で、Effective Java Item 18（継承よりコンポジションを選ぶ）の実践例になっている
- Spring AOPも実質的にDecoratorパターンの一種（ログ・トランザクション・セキュリティなどの横断的関心事を、既存のビジネスロジックに触れずに追加する仕組み）と理解できた
- 課題6（Strategy）・課題7（Observer）・課題25（Decorator）は、いずれも「既存コードに触れず新しいクラスを追加するだけで機能拡張できる」という開放閉鎖原則を目指す点で共通しているが、それぞれ実現方法が異なる
  - Strategy：複数の実装を「切り替える」（1つを選んで使う）
  - Observer：1つの出来事に対して「複数が反応する」（並行して複数が動く）
  - Decorator：既存の処理を「包んで、前後に処理を足す」（順番に重ねて動く）
- 今回は該当箇所がなかったが、もし将来メール送信にリトライやログ機能を追加する要件が出てきた場合、この設計パターンをそのまま適用できる

**⑤ 編集例**

```java
        logger.info("メール送信完了: {}", email);

    }

```

課題文の修正後コード：
```java
public interface MailService {
    void send(String to, String subject, String body);
}

@Component
public class SimpleMailService implements MailService {
    private final MailSender sender;

    @Override
    public void send(String to, String subject, String body) {
        SimpleMailMessage msg = new SimpleMailMessage();
        msg.setTo(to);
        msg.setSubject(subject);
        msg.setText(body);
        sender.send(msg);
    }
}

public class LoggingMailService implements MailService {
    private final MailService delegate;

    public LoggingMailService(MailService delegate) {
        this.delegate = delegate;
    }

    @Override
    public void send(String to, String subject, String body) {
        log.info("メール送信開始: to={}", to);
        delegate.send(to, subject, body);
        log.info("メール送信完了: to={}", to);
    }
}

public class RetryableMailService implements MailService {
    private final MailService delegate;
    private final int maxRetries;

    @Override
    public void send(String to, String subject, String body) {
        for (int i = 0; i < maxRetries; i++) {
            try {
                delegate.send(to, subject, body);
                return;
            } catch (Exception e) {
                if (i == maxRetries - 1) throw e;
                log.warn("メール送信失敗、リトライします: {}/{}", i + 1, maxRetries);
            }
        }
    }
}

@Bean
public MailService mailService(SimpleMailService simple) {
    return new RetryableMailService(
        new LoggingMailService(simple),
        3
    );
}
```

- Decoratorパターン（既存オブジェクトを包んで、機能を動的に追加する設計）
- 委譲（delegation）
- Effective Java Item 18：継承よりコンポジションを選ぶ
- Spring AOPとDecoratorパターンの関係
- Strategy・Observer・Decoratorの目的（開放閉鎖原則）は共通するが、実現方法（切り替え・並行反応・包んで重ねる）が異なること

**⑦ 理解度の自己評価**
◯（「委譲」「玉ねぎのように包む」という仕組みと、新機能追加時に既存クラスへ影響が及ばない理由を、自分の言葉で説明できた）

## 課題番号：12（カスタムバリデーションの実装編）

**① 該当箇所**
- OrderForm.java：destinationZipcode（郵便番号）、destinationTel（電話番号）
- InsertForm.java：zipcode（郵便番号）、telephone（電話番号）
- PhoneNumber.java：新規作成
- PhoneNumberValidator.java：新規作成
- PostalCode.java：新規作成
- PostalCodeValidator.java：新規作成

**② なぜ問題なのか**
`OrderForm`・`InsertForm`の両方に、電話番号・郵便番号の正規表現（`@Pattern(regexp = "...")`）が全く同じ内容で重複して書かれていた。修正のたびに全箇所を漏れなく直す必要があり、片方だけ修正して片方を直し忘れると、画面によってバリデーションルールが異なってしまうという不整合が生まれる（例：注文フォームでは新しい電話番号形式が通るのに、ユーザー登録フォームでは古い形式のまま弾かれてしまう、という状況が起こりうる）。

**③ なぜこのように修正したのか**
Bean Validationのカスタムバリデーションアノテーションを実装した。1つのバリデーションルールにつき、アノテーション本体（宣言）とConstraintValidator実装（検証ロジック）の2ファイルを1セットとして作成する。

- `@PhoneNumber` / `PhoneNumberValidator`：正規表現`^[0-9]+-[0-9]+-[0-9]+$`による電話番号チェック
- `@PostalCode` / `PostalCodeValidator`：正規表現`^[0-9]{3}-[0-9]{4}$`による郵便番号チェック

`@Constraint(validatedBy = XxxValidator.class)`という記述で、アノテーションとValidatorを紐付ける。これにより、正規表現の実体はValidator側の1箇所にのみ存在し、各フォームクラスにはアノテーション（`@PhoneNumber`・`@PostalCode`）を貼るだけで済むようになる。将来、電話番号の正規表現を変更したくなった場合も、`PhoneNumberValidator`の1箇所を直すだけで、`@PhoneNumber`を使っている全てのフォームに反映される。

`OrderForm`・`InsertForm`それぞれの`@Pattern(regexp = "...", message = "...")`を、`@PostalCode`・`@PhoneNumber`に置き換えた。`InsertForm`には`password`フィールドの複雑度チェックにも`@Pattern`が使われていたため、こちらは`@Pattern`自体の`import`を削除せず残す判断をした（今回のカスタムバリデーション対象は郵便番号・電話番号のみで、パスワードの複雑度チェックは対象外のため）。

**④ 気づきや他の改善策**
- カスタムバリデーションアノテーションの作成コストは一定かかるが（アノテーション定義＋Validator実装の2ファイル）、複数のフォームで使い回すほど、その後の保守コストが下がるというトレードオフがある。今回は2つのフォームで重複していたため、明確にコストに見合う対応だった
- `isValid()`メソッドの中で`if (value == null || value.isBlank()) return true;`としているのは、null・空文字のチェックは`@NotBlank`に責任を委譲するためである。1つのアノテーションに複数の責務（必須チェック＋形式チェック）を持たせないという設計判断
- DBアクセスが必要なバリデーション（例：メールアドレスの重複チェック）も、同じ仕組みでSpringの`@Autowired`をValidatorに注入することで実現できる（今回は未実装だが、応用範囲が広いと理解した）
- 同じ「重複を1箇所にまとめる」という目的でも、課題17（Factory Method）は「オブジェクトの組み立て方」を1箇所にまとめ、今回（カスタムバリデーション）は「値の検証ルール」を1箇所にまとめるという違いがある。目的に応じて適切な仕組みを選ぶ必要があると理解した

**⑤ 編集例**

## 課題番号：14（DBのパフォーマンスチェック——インデックス・テーブル設計編）

**① 該当箇所**
- orders.user_id：インデックスなし
- order_items.order_id：インデックスなし
- order_toppings.order_item_id：インデックスなし
- sql/Migration/5_add_indexes.sql：新規作成

**② なぜ問題なのか**
`orders.user_id`・`order_items.order_id`・`order_toppings.order_item_id`は、いずれも外部キーとしてJOINやWHERE条件に頻繁に使われるカラムだが、インデックスが設定されていない。

- `orders.user_id`：`OrderRepository.findByOrdertable()`のWHERE条件で使用
- `order_items.order_id`：`OrderRepository.orderLoad()`・`findByOrdertable()`のJOIN条件で使用
- `order_toppings.order_item_id`：同上のJOIN条件で使用

インデックスがない状態では、これらのカラムを条件にした検索・結合のたびにフルテーブルスキャン（Seq Scan）が発生する。テーブルの先頭から1行ずつ条件に合うか確認していくため、データ量が増えるほど検索にかかる時間が線形に悪化する。`users.email`にはUNIQUE制約がついており、PostgreSQLではUNIQUE制約に対して自動的にB-treeインデックスが作成されるため、この副産物として検索も高速化されている状態だった。一方、`orders.user_id`等にはそうした保証がなく、同じ問題を抱えていた。

**③ なぜこのように修正したのか**
外部キーとしてJOIN・WHERE条件に使われるカラムには、フルテーブルスキャンを防ぐためインデックスを追加するのが基本方針である。`CREATE INDEX`文を用いて、3つのカラムそれぞれにインデックスを作成するSQLを、既存のマイグレーションファイル群（`3_add_foreign_keys.sql`・`4_add_check_constraints.sql`）に続く形で`5_add_indexes.sql`として新規作成した。

`EXPLAIN`コマンドを使うことで、実際にSQLを実行することなく「このクエリがどのように実行される予定か」という実行計画を確認できる。インデックスがない状態では結果に`Seq Scan`（全件走査）と表示され、インデックスを追加すると`Index Scan`に変わることで、改善を客観的に確認できる。

**④ 気づきや他の改善策**
- 最初、`orders.user_id`だけが対象だと考えていたが、`order_items.order_id`・`order_toppings.order_item_id`も同じ構造の問題（外部キーがJOIN・WHERE条件に使われている）を抱えていることに気づいた。1つのテーブルを個別に見るのではなく、「外部キーカラムを見つけたら、反射的にインデックスの有無を確認する」という視点を持つことの重要性を実感した
- `UNIQUE`制約は「重複チェックのためのB-treeインデックス」を自動生成するため、副産物として検索も高速化される。制約とインデックスの関係を理解できた
- インデックスは検索を速くする一方で、INSERT・UPDATE時にはインデックスの更新コストがかかるため、「闇雲に増やせばよい」わけではなく、実際によく使われるカラムに絞って追加すべきという原則も併せて理解した
- 一意制約（UNIQUE）をつけると自動的にインデックスが作られる、という点は`users.email`の例で確認できたが、他のUNIQUE制約付きカラムがあるかも今後確認する余地がある

**⑤ 編集例**

```sql

-- 外部キーとしてJOIN・WHERE条件に使われるカラムには、
-- フルテーブルスキャンを防ぐためインデックスが必要

CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_toppings_order_item_id ON order_toppings(order_item_id);
```

**⑥ 学んだ概念・用語**
- フルテーブルスキャン（Seq Scan）とインデックススキャン（Index Scan）
- `EXPLAIN`コマンドによる実行計画の確認
- B-treeインデックスの仕組みと計算量（O(n) → O(log n)）
- UNIQUE制約とインデックスの自動生成の関係
- 外部キーカラムには原則インデックスを追加するという設計指針

**⑦ 理解度の自己評価**
◯（`orders.user_id`だけでなく、同じ構造を持つ他の外部キーカラムにも同様の問題が及ぶことを、自分で気づき直せた）

**⑧ 同様の変更箇所（未対応）**

## 課題番号：32（LIKE検索のインデックス問題編）

**① 該当箇所**
- ItemRepository.java：findByName()
- sql/Migration/6_add_trgm_index.sql：新規作成

**② なぜ問題なのか**
`ItemRepository.findByName()`は、`"%" + name + "%"`という形で商品名を検索しており、`WHERE name LIKE '%カレー%'`のような中間一致検索を行っている。

B-treeインデックスは「先頭の文字」を手がかりに整理された仕組みである（辞書が五十音順に並んでいるのと同じ）。しかし中間一致検索（`%word%`）は、対象の文字列が商品名の先頭・真ん中・末尾のどこにあるか分からないため、「先頭の文字から絞り込む」というB-treeの仕組みが機能しない。そのため、たとえ`items.name`にインデックスがあったとしても、この検索方法ではフルテーブルスキャン（Seq Scan）になってしまう。前方一致（`LIKE 'word%'`）であればB-treeインデックスが使えるが、今回は中間一致のため通常のインデックスでは解決できない問題だった。

**③ なぜこのように修正したのか**
PostgreSQLの`pg_trgm`拡張機能を使い、通常のB-treeとは異なる仕組み（トライグラム＝文字列を3文字ずつの断片に分解して索引を作る特殊なインデックス）を導入する。トライグラムインデックスであれば、文字列のどこに対象の文字が含まれているかに関わらず検索できるため、`LIKE '%カレー%'`のような中間一致検索でもインデックスが機能するようになる。

`CREATE EXTENSION IF NOT EXISTS pg_trgm;`で拡張機能を有効化した上で、`CREATE INDEX idx_items_name_trgm ON items USING GIN (name gin_trgm_ops);`によりGINインデックス（トライグラム用のインデックス方式）を作成する。

**④ 気づきや他の改善策**
- 課題文にはもう一つの対策として`LIMIT`による件数制限が挙げられていたが、これは検索の重さ自体（DBが内部で何件調べる必要があるか）をほとんど改善しない。特に今回のSQLのように`ORDER BY price_m`と`LIMIT`が組み合わさっている場合、「条件に合う行を全部集めてから並べ替えて、最後に指定件数だけ切り出す」という動きになりやすく、結局はフルテーブルスキャンが必要になる。`LIMIT`は「画面に返す結果件数を減らす」という別の観点での対策であり、根本解決にはならないと理解した
- 課題14（インデックス追加）と課題32（LIKE検索のインデックス問題）は、どちらも「インデックスが効いているか」というテーマで共通しているが、課題14は「インデックスが存在しない」ことが問題で、課題32は「インデックスがあっても検索方法によっては機能しない」ことが問題という違いがある。インデックスの有無だけでなく、検索条件の書き方（前方一致か中間一致か）によって効果が変わることを学んだ
- 検索機能が重要な場合はElasticsearchなどの全文検索エンジンの導入も選択肢になるが、今回の規模では`pg_trgm`で十分な対応と判断した

**⑤ 編集例**

```sql
-- リファクタリング課題#32 LIKE検索のインデックス問題
-- LIKE '%word%' の中間一致検索はB-treeインデックスが機能しないため、
-- pg_trgm拡張機能によるトライグラムインデックスを追加する

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_items_name_trgm ON items USING GIN (name gin_trgm_ops);
```

**⑥ 学んだ概念・用語**
- B-treeインデックスと前方一致・中間一致検索の関係
- `pg_trgm`拡張機能とトライグラム（3文字断片）インデックス
- GINインデックス（Generalized Inverted Index）
- `LIMIT`と`ORDER BY`を組み合わせた場合の実行計画の挙動
- 検索方法（前方一致・中間一致・後方一致）によってインデックスの効果が変わること

**⑦ 理解度の自己評価**
◯（なぜB-treeが中間一致検索で機能しないかを、「先頭の文字を手がかりにする仕組み」という観点から自分の言葉で説明できた。`LIMIT`が根本解決にならない理由についても、ORDER BYとの組み合わせを踏まえて理解できた）

**⑧ 同様の変更箇所（未対応）**
特になし（対象と判断した`items.name`のLIKE検索に対応済み）
